# AWS execution for #362 C2 (L0.3 SCIENTIFIC outcome source)

Issue: lisbun/lisjong-arena#362（parent lisbun/lisjong-project#79 C2）。

Issue #362の500半荘（TRAIN 400 / SELECT 100）を、ローカルPCをcontrol plane、単一EC2を
data planeとして生成するための**#362専用**operator wrapperである。汎用AWS
frameworkではなく、multi-instance分散もしない。

## Scientific contractは変えない

- scientific producerはArena `1a14855832315abfe30244d68b7ea6498c3370a0`の
  `lisjong_arena.focal_outcome_source`をそのまま使う。instanceはこのrevisionを
  clean detached checkoutし、`build_source_contract()`はそこで作る
- `scripts/aws/generate_l03_c2_362.py`はfrozen checkoutの**外**に置かれるoperator
  driverで、`generate_focal_outcome_source()`のper-game body
  （`run_focal_game` -> `write_game`）だけをspawn worker processで並列実行する
- 出力はglobal `game_ordinal` 0..499のcanonical順に再構成してから、producerの
  `build_manifest` / `verify_focal_outcome_source` / renameで公開する。worker数・
  完了順・時刻はmanifestへ入らない。1 gameでも失敗すれば何も公開しない
- tooling revisionは`src/`と`pyproject.toml`を変更しないことをpreflightで検証する

同じpopulationに対して、sequential producerとparallel driverの出力がbyte一致する
ことを`tests/test_l03_c2_362_driver.py`（test専用900000台seed）で固定している。

## 手順

```powershell
# request: 各allocationのreserve commit時点のledger snapshotからbindingを作る
.\.venv\Scripts\python.exe scripts\aws\generate_l03_c2_362.py build-request `
  --train-ledger <ledger@TRAIN reserve commit> --train-allocation <TRAIN id> `
  --select-ledger <ledger@SELECT reserve commit> --select-allocation <SELECT id> `
  --output <request.json>

# no-billing preflight: Pricing API / quota / offering / dry-run / cost plan
.\scripts\aws\run-l03-c2-362.ps1 -Action Preflight -RequestPath <request.json> `
  -ToolingRevision <pushed wrapper commit> -AwsProfile lisbun-admin

# billable: bucket -> volume -> instance -> fail-safe -> SSM submit -> Collect
.\scripts\aws\run-l03-c2-362.ps1 -Action Launch ...

# 進捗 / 再接続（再投入はしない）
.\scripts\aws\status-run.ps1 -RunId <run-id> -AwsProfile lisbun-admin
.\scripts\aws\run-l03-c2-362.ps1 -Action Collect -RunId <run-id> -AwsProfile lisbun-admin
```

`Collect`はremote完了を確認してEC2をterminateし、S3からtarballを取得して
remote / object / localのSHA-256一致を確認し、localで`readback`（Arena strict
verify、pinned lisjong `read_outcome_source()`、`build_outcome_targets()`、#79
preflight facts / frozen hard stop）を実行し、残存resourceを確認する。

## Failure diagnostics

失敗時もpartial sourceは公開しない。scientific manifest / source identityとは別に、
次のoperational evidenceを残す。

- `bootstrap.log`はretained artifact volumeの`issue-362/operational/`にも保存する
  （root diskはtermination時に削除されるため）
- driverは中断原因のgameについて`failure-record.json`（`game_ordinal`、`seed`、
  `split`、`focal_seat`、exception class / message / worker traceback）を同じ
  operational directoryへ書く
- bootstrapは失敗時にfailure recordとlog末尾をSSM outputへ出し、`Collect`は
  それをlocal run directoryの`failure-record.json`へ保存する

## Cost bound

planning basisは#361 C0のlocal実測35.40 s/hanchanで、#340相当のpaid matching
calibrationは使わない。preflightはPricing APIの現在価格からEC2 + root EBS +
public IPv4 + retained EBS + S3 / transfer + safety marginが`-CostBudgetUsd`
（既定USD 5）以下となるlaunch-clock windowを計算し、予測billable上限の1.5倍を
確保できない場合はlaunchしない。同じ絶対deadlineでboot時user-data timerと
SSM timerの二重fail-safeを張る。

## Retained resources

- encrypted 8 GiB gp3 artifact volume: local readbackがPASSするまで保持。
  `-Action DeleteVolume`はdownload / SHA-256 / strict readback / #79 preflight /
  local保存先が全て確認済みの場合だけ削除する
- temporary S3 bucket（`lisjong-362-c2-<account>-<suffix>`）: Block Public Access
  4項目、BucketOwnerEnforced、SSE-S3、instance roleへは2 objectへの`s3:PutObject`
  だけをbucket policyで許可（IAM roleは変更しない）、non-TLS deny。#79 preflightと
  #362結果記録後に`-Action DeleteBucket -ResultRecorded`で削除する
